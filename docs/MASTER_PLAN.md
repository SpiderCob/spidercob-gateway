# Spidercob Gateway — Master Plan

**Purpose of this doc:** the single place that says *what we're building, why, and what to do next*. `design.md` is the strategy/spec rationale (why ID-JAG, why this architecture, GTM, funding) — read that for the "why." This doc is the living execution tracker — read it first in every session, update it as ground truth changes. When the two disagree, this doc wins on *status*, `design.md` wins on *rationale*.

---

## 0. North Star

**One sentence:** The open-source MCP gateway for teams without an IAM department — spec-correct agent identity (ID-JAG / MCP Enterprise-Managed Authorization) and traffic inspection (DLP, injection defense), in one container, running in 15 minutes.

**The problem we're killing:** every internal MCP server today is either wide open or protected by a static API key nobody rotates. Non-human identities (agents, service accounts) outnumber humans ~100:1, and there's no open-source resource-side gateway that gives every MCP request a real, attributable identity (human `sub` + acting agent `act`) and inspects what flows through it.

**What winning looks like, by horizon:**

| Horizon | Looks like |
|---|---|
| **OSS launch** (end of Phase 4) | Anyone can `docker compose up`, protect a real MCP server, and see a secret get redacted — in under 15 minutes, no IdP required. |
| **90 days post-launch** | 1.5–3k stars, 50+ weekly-active gateways, 3 external contributors, one IdP-vendor co-marketing touch. |
| **180 days** | 100–150 weekly-active gateways, 5+ design partners running it in production, first inbound "we'd pay for managed." |
| **Funded** | Managed control plane exists; OSS core stays fully-featured (the seam is operational scale, never withheld security). |

**Non-negotiables that protect the north star** (violating these forfeits the whole bet — see `design.md` §2, §12):
- The gateway must be **spec-correct** ID-JAG/EMA — not a custom JWT with an `allowed_mcps` claim. That was the v0.1 mistake; redoing it kills the differentiation.
- **Never a multi-audience token.** One access token = one MCP server, always (RFC 8707). This is the confused-deputy protection the whole design hinges on.
- **Fail static, never fail open** — if policy sync or the tunnel drops, keep enforcing last-known policy.
- **Identity + content inspection in one box** is the unclaimed wedge (§12). Don't let either half atrophy relative to the other.
- **The data plane never leaves customer infrastructure — in every tier, no exception.** The container that actually enforces policy and touches live MCP traffic always runs on customer-owned infrastructure. Spidercob never operates or routes a customer's production MCP traffic itself — no one will trust a third party with that, and it's not a cost/liability worth carrying either. Anything Spidercob operates (a future SaaS control plane) is limited to policy authoring and config sync; it is never inline on the request path. See §6 decision log, 2026-08-03.

## 1. What We're Building, End to End

One Go binary, one container, three logical planes:

```
Agent / MCP client
     │ (1) gets identity: local login (Mode A) or enterprise IdP token exchange (Mode B)
     ▼
┌─────────────────────────── SPIDERCOB GATEWAY ───────────────────────────┐
│  Identity Engine          Control Plane            Data Plane           │
│  embedded IdP OR          Admin UI + REST API       (the hot path)      │
│  ID-JAG consumer,         users/groups/nodes/        authN → policy →   │
│  OAuth 2.1 AS,            policies/audit             sanitize → route → │
│  JWKS, per-node                                       DLP-scan → audit  │
│  access tokens                                                          │
└───────────────────────────────────────────────────────────────────────┘
     │ (2) exchanges identity for a short-lived, single-audience token
     ▼
(3) JSON-RPC over the token  ──▶  gateway validates + enforces policy  ──▶  internal MCP servers
                                                                              (Jira, Postgres-RO, ...)
```

**The three identity modes** (design doc §2.3 — build Mode A first, it's a strict subset of B):

- **Mode A — Standalone.** Gateway is its own IdP: local users, CSV upload, argon2id passwords. No customer IdP required. This is the on-ramp for the target buyer (50–100-person startup, no IAM team).
- **Mode B — Federated (the actual ID-JAG spec flow).** Customer's IdP (Okta/Entra/Keycloak) issues ID-JAGs via RFC 8693 token exchange; the gateway's AS validates and exchanges them for per-node access tokens via RFC 7523. This is what makes the "spec-correct" claim real.
- **Mode C — Managed.** A or B, plus policy pushed from a Spidercob SaaS control plane. **Do not build before funding** — zero OSS-traction value, explicit scope cut (§13.3). **Data-plane note:** even in Mode C, the enforcing gateway container runs on the customer's own infrastructure. The SaaS control plane authors policy and pushes signed bundles down an outbound tunnel — it never sits inline on live traffic. There is no tier where Spidercob operates the actual proxy on a customer's behalf.

**Mode C enrollment and registration mechanism (post-funding, but recorded now before it's lost — 2026-08-06):** the SaaS control plane can never reach a customer's MCP servers directly (data-plane-customer-only, §0), so registration is a two-step, control-plane-mediated flow, not a direct probe:
1. Admin generates a short-TTL, **single-use enrollment token** in the control plane UI (hashed at rest, tenant-scoped). The container is **one generic image for every tenant** — never a custom-baked-per-tenant image — deployed with that token as an env var. Baking policy into a unique per-customer image was the original instinct, but it can't work anyway: tool discovery (below) requires a *live, already-connected* gateway to do the probing, so there's nothing to bake in before first boot.
2. On first boot, the container generates its own Ed25519 keypair **locally — the private key never leaves the customer's machine** — and calls the control plane's `/enroll` endpoint with the token and its public key. The control plane validates and burns the token (single-use, can't be replayed), records the public key against a new `gateway_instances` row, and returns a control-plane-signed instance identity plus the tenant's current policy bundle as the first sync. Every connection after that authenticates with the gateway's own keypair, never the original token again. (Same pattern as Kubernetes `kubeadm join` tokens or Tailscale auth keys — bootstrap credential vs. long-lived identity, kept separate.)
3. **Tool discovery is gated on step 2 having already happened.** Admin can register MCP node *metadata* (name, URL — no probe needed) as a pending record before any container is deployed, but the actual `tools/list` probe can only run *after* a gateway is enrolled and connected: control plane sends a `ProbeNodeRequest` down the tunnel, the connected gateway does the live probe locally (it can reach the customer's own network), and reports back **metadata only** (tool names, descriptions, schema hashes — never payloads) for the admin to assign per-group access to in the SaaS UI.

**Non-human identities (NHI) are first-class principals, not an afterthought.** Every group can contain both human users and agents (`user_groups` and `agent_groups`, §8) — an NHI (a scheduled job, a standing automation) gets its *own* minimal group assignment, never inherited from whichever human registered it, so least-privilege actually holds for automated access. NHI authentication is decoupled from whichever mode a tenant's humans use — an org fully on Okta SSO still needs a local, IdP-agnostic way to onboard a CI job. Two credentialing tiers by NHI shape (see §6, 2026-08-04): a static, hashed client secret for ephemeral/stateless NHIs that can't hold a key between runs (v1); a locally-generated keypair enrolled the same way the gateway container itself enrolls, for long-running NHIs that can (v1.1, "secretless"). This is the other half of the NHI market thesis (design doc §12) — the sprawl problem is as much "who remembers this credential exists six months later" as it is "can this agent get in," so last-used tracking and stale-credential flagging in the admin UI matter as much as the access-control mechanics.

**The request lifecycle every JSON-RPC call goes through** (design doc §6):
1. TLS terminate, parse JSON-RPC, reject malformed/oversized early.
2. Validate bearer token — signature, `exp`, `aud` matches this node, `jti` not revoked.
3. Policy check — server → method → tool → (v1.1) parameter level.
4. Inbound sanitization — schema enforcement against the pinned `inputSchema`, injection heuristics, size/recursion caps.
5. Forward upstream with a gateway-held credential (the agent's token never reaches the MCP server).
6. Outbound DLP scan on the response — secrets, PII, response-embedded injection; redact structurally, never drop silently.
7. Hash-chained audit record: `sub`, `act`, node, method, tool, decision, scanner verdicts, latency.

**The two "moats" we're claiming** (§12.3): nobody doing spec-correct identity also inspects content, and nobody inspecting content also does spec-correct identity. Both halves have to ship, or the positioning collapses into "yet another gateway."

## 3. Step-by-Step Plan From Here

Each step has a **Definition of Done (DoD)** — don't mark it done, or let Claude mark it done, without meeting it. Steps are dependency-ordered; don't skip ahead to policy before tokens exist, or scanning improvements before schema enforcement (schema enforcement kills a whole injection class for free — do it before hand-rolling more regex).

### Phase 1 — finish the skeleton (close out what's open)

Full spec: [GitHub issue #1](https://github.com/SpiderCob/spidercob-gateway/issues/1). **Build in this order, not by grouping** — the test design needs both transports (HTTP and stdio) available together for session-mapping and idle-timeout tests, so a minimal stdio path has to exist *before* those, not be bolted on after (§6, 2026-08-06):

1. [x] **Streaming-safe scanning groundwork.** Genuinely independent of everything else here — decide now how SSE chunks will be buffered/scanned later (Phase 3), even though full windowed redaction isn't implemented yet, so the interface shape doesn't need to change later. Cheap, unblocks nothing, unblocked by nothing — do it first and move on.
2. [x] **Minimal stdio proxying.** Child-process supervisor spawns a local stdio MCP server, pipes its stdio, and exposes it as a node — same routing shape as an HTTP-backed node. **No crash supervision yet** — that's step 5. Pulled forward specifically so a second transport exists while session mapping and idle timeout are being built and tested, not after. *DoD: at least one real stdio server runs behind the gateway end-to-end via the same request path as an HTTP node.*
3. [x] **Session mapping**, built and tested against **both** transports from the start. The gateway mints its own client-facing session ID at `initialize` — never passes through the upstream's raw session ID — and maintains a local mapping `gateway_session_id → (node, upstream_session_id_or_process_handle)`. The `initialize` response sets both the `Mcp-Session-Id` header (spec-required) and a mirrored session cookie with the same value, so native cookie-based cloud-LB stickiness works out of the box for v1.1 HA without customers hand-configuring header hashing (§6, 2026-08-04). On revocation/`DELETE`, the gateway tears down the corresponding upstream session/process and removes the mapping; further requests bearing that session ID are rejected immediately, not silently re-created. *DoD: killing a session server-side actually terminates the upstream connection or child process — verified against both an HTTP node and a stdio node.*
4. [x] **Idle session timeout**, same dual-transport testing as above. Sessions with no activity for a configurable duration are automatically torn down the same way as explicit revocation — mapping removed, upstream session/process reaped. Prevents orphaned upstream sessions and orphaned stdio child processes from accumulating indefinitely. *DoD: an idle session past its timeout is fully gone (mapping + upstream resource) without any client action.*
5. [x] **Full stdio process supervision**, layered on top of the minimal proxying from step 2, now that a real session lifecycle exists to hook into: restart on crash with exponential backoff (the standard pattern — systemd `Restart=on-failure`+`RestartSec`, Kubernetes `CrashLoopBackOff`, supervisord `autorestart`+`startretries`); after N rapid crashes within a window, stop auto-restarting and quarantine the node (mark unhealthy, alert admin) instead of looping forever; an in-flight session tied to a crashed process fails cleanly back to the client via the teardown path built in step 3 (forcing re-`initialize`) rather than hanging. Per the MCP spec, stdio servers must write only protocol JSON-RPC to stdout and everything else to stderr — treat a non-parseable stdout line as a logged protocol-violation warning (not fatal for one bad line), but count repeated violations toward the same quarantine threshold as crashes. *DoD: a simulated crash auto-restarts with backoff; a simulated crash-loop gets quarantined rather than looping forever.*

**Phase 1 complete (2026-08-07)** — merged via [PR #2](https://github.com/SpiderCob/spidercob-gateway/pull/2), closing [issue #1](https://github.com/SpiderCob/spidercob-gateway/issues/1). Session-lifecycle sequence diagrams for both transports, plus the stdio-only crash/self-heal path, are in `docs/session-lifecycle.md`. Real end-to-end validation is now a runnable command, not a manual step — `make ci` (`automation/`), which every future issue extends rather than re-inventing.

**stdio nodes are explicitly out of scope for multi-replica HA (§6, 2026-08-04).** A stdio node is pinned to whichever single gateway instance spawned it — v1.1 HA (policy replicated to N independent replicas) is scoped to HTTP-transport (streamable_http/SSE) nodes only. Don't build inter-replica stdio ownership/failover — that would require exactly the risky node-to-node coordination the control-plane-only distribution model is designed to avoid. A customer wanting HA for a stdio-backed server should front it with its own networked HTTP wrapper instead.

### Phase 3 — Policy & scanning

**Split into 3a/3b/3c (2026-08-07), not one bundled issue** — unlike the Phase 2a/2b split (driven by genuinely different test infrastructure, Docker vs. not), this split is for reviewability: the three items below are only loosely coupled, and bundling them would make one issue/PR span a policy engine, a rug-pull defense mechanism, and a scanner rewrite. All three stay pure-Go, `httptest`-testable — no infra reason to split, just size.

7. [x] **Phase 3a — [GitHub issue #7](https://github.com/SpiderCob/spidercob-gateway/issues/7): `internal/policy` v0** — replaced `DenyAll` with a real evaluator: server-level → method-level → tool-level, backed by the store, explicit **ALLOW and DENY rule types** (not allow-only), evaluated as deny-overrides-allow-overrides-default-deny (§6, 2026-08-04). **`tools/list` response filtering** (unauthorized tools become invisible, not just blocked — the specific prompt-injection defense this was meant to be, not a nice-to-have). **Rate limiting/quota per group or per NHI** (precedented by spider-snoop's own credit-based throttling) — in-memory, per-process, defense-in-depth, exactly the "approximate enforcement is fine for v1" posture already decided (§6/§7). **Scan-verdict-conditional actions** (`block_on_scan_flag`): a policy rule can escalate the existing scan chain's log-only verdicts (e.g. injection heuristics) to an actual block, for specific tools/groups — closes the gap where `scan` and `policy` were disconnected pipeline stages, using the *existing* two-scanner pipeline (richer scanning is 3c, not built here).
   - *DoD, met:* a request for a tool outside the caller's group policy is rejected (403) and that tool does not appear in that caller's `tools/list` response. A request for an authorized tool succeeds end-to-end — proven against the real compiled binary by `automation/run-e2e-policy.sh`, the first e2e script in this repo's history to reach a real `200` on a policy-gated call rather than stopping at a `403`/`401`. A rate-limited request gets `429`, distinct from a denied request's `403`. An injection-flagged request without `block_on_scan_flag` is flagged, not blocked (honest default preserved); with it, the same flagged content is blocked.
8. [x] **Phase 3b — [GitHub issue #9](https://github.com/SpiderCob/spidercob-gateway/issues/9): `internal/pin` — tool pinning (rug-pull defense).** TOFU (trust-on-first-observation, the same model SSH host keys/TLS cert pinning use — chosen specifically because no admin approval flow exists yet to make a real trust decision with): the first `tools/list` a node ever produces becomes its trusted baseline automatically, one hash per tool covering name+description+inputSchema together (inputSchema's JSON key order canonicalized first, so reordering never false-positives as drift). **Drift detection is a periodic background refresh, not continuous per-request diffing** — keeps the hot path fast (latency budget, design doc §16); refresh interval is admin-configurable per node (`config.Node.PinRefreshIntervalSeconds`, falling back to `config.PinRefreshIntervalSeconds`), with a separate, normally-much-shorter `config.PinCheckIntervalSeconds` controlling how often the scheduler wakes up to check *whether* any node is due. Quarantine is scoped per-tool, not per-node — one drifted tool never takes down every other tool on the same server. Pins (and quarantine state) are persisted and **never re-established on restart** — this is load-bearing, not incidental: re-establishing on every boot would let an attacker trivially bypass the whole defense by waiting for (or triggering) one. Composes into the exact two seams issue #7 already built for policy: the `tools/call` gate (a call must be both policy-authorized and not quarantined) and `tools/list` filtering (a tool must be both authorized and not quarantined to be visible) — a quarantined tool's rejection is distinguishable from a policy denial in both the response body and the logs (story 24), so an operator debugging a 403 isn't left guessing which of two independent mechanisms fired.
   - *DoD, met:* a real stdio node's tool gets TOFU-pinned on first contact; a simulated definition change (rewriting the fixture's description file between refresh cycles) is caught within one refresh cycle; the drifted tool is confirmed both rejected via `tools/call` and absent from `tools/list` — proven against the real compiled binary by `automation/run-e2e-pin.sh`, not simulated with mocks.
9. [x] **Phase 3c — [GitHub issue #11](https://github.com/SpiderCob/spidercob-gateway/issues/11): `internal/scan` upgrades.** Schema enforcement against pinned `inputSchema` — a new composed check at the `tools/call` gate, not a `Scanner` (it needs node/tool context the byte-only `Scanner` interface can't express), via a new pure `pin.ValidateArguments` using `google/jsonschema-go`; required the `tool_pins` table to actually persist the raw pinned schema (a new `input_schema` column), not just its hash, since a hash can't be un-hashed back into the schema needed for validation. Gitleaks-derived secret rule expansion (Azure/Stripe/GitHub/DB-connection-string patterns added to the original five). A new entropy scorer (flag-only, unknown-shaped secrets — Shannon entropy over regex-extracted candidate tokens, ordered after `SecretScanner`/`PIIScanner` in `Default()`'s chain so an already-redacted value is gone from the body by the time it runs, never double-flagged). A new PII scanner (Luhn-validated credit cards + plausibility-filtered SSN redacted by default; email/phone flag-only and off by default via new `config.ScanDetectEmail`/`ScanDetectPhone` fields). Homoglyph/zero-width normalization *before* injection-heuristic pattern matching (detection-only — matches against a normalized copy, never mutates the real bytes returned to/from the client). Honest defaults preserved throughout: existing secret-redaction behavior unchanged, flag-don't-block injection heuristics preserved (issue #7's `block_on_scan_flag` still lets a specific policy rule override that default per tool/group).
   - *DoD, met:* a real tools/call with arguments that don't match a tool's pinned schema is rejected (403, reason distinguishable as a schema violation) before ever reaching the upstream — proven against the real compiled binary and a real stdio fixture (whose `inputSchema` is the MCP go-sdk's own real, inferred schema, not hand-crafted) by `automation/run-e2e-schema.sh`. All four new/expanded scanners are independently unit-tested (`internal/scan`), and the schema-enforcement seam is proxy-level `httptest`-tested (valid call succeeds; no-pin-yet and pinned-with-no-schema both never block).

**`tools/list` filtering and pagination (issue #7):** the upstream's pagination cursor is treated as fully opaque and passed through unchanged — never recomputed. The `tools` array is filtered in place per page; a filtered page coming back thinner than the upstream's original, or even empty, is spec-legal (MCP clients aren't supposed to assume fixed page sizes) and accepted for v1. Auto-advancing through fully-empty filtered pages on the client's behalf remains a later UX polish, not a v1 correctness requirement.

**Phase 3 DoD (full, all three sub-phases — Phase 3 is now complete):** a request for a tool outside the caller's group policy is rejected (403) and that tool does not appear in that caller's `tools/list` response — **met, issue #7**. A request for an authorized tool succeeds end-to-end — **met, issue #7**. A simulated upstream schema change on an already-approved tool gets quarantined within one refresh interval and blocked — **met, issue #9** (re-*approval* specifically stays Phase 4, per issue #9's explicit out-of-scope: quarantine has no clearing mechanism yet). A tool-call whose arguments don't match its pinned `inputSchema` is rejected before reaching the upstream — **met, issue #11**. A secret embedded in a tool response is redacted before reaching the client, with a corresponding audit record — redaction (now with an expanded pattern set, plus entropy-based and PII detection) is met; the audit-*record* half is still unbuilt (`internal/audit` doesn't exist), unchanged by issue #11 — logging via `slog` is not the same as a queryable, hash-chained audit trail. An injection-flagged request is flagged, not blocked, per the honest default, unless a policy rule opts it into blocking — **met, issue #7**, now evasion-resistant to homoglyph/zero-width substitution too (issue #11). All of the above that are met are automated tests against the real compiled binary or the interop harness, not manual verification.

## 6. Decisions Log (resolved — don't relitigate without a real reason)

- **2026-08-03 — Reverse proxy only, no forward-proxy/egress-DLP mode.** The gateway enforces policy in front of *registered* MCP nodes; it does not become a general "route all your traffic through us" proxy. See §4.
- **2026-08-03 — Default-deny confirmed as the policy model** (already `design.md` §5; explicitly re-confirmed here with rationale). Reasons: (1) you can't enumerate the danger space in advance — default-allow means every newly-added tool is reachable by everyone until someone remembers to block it; (2) it's the only model consistent with tool pinning, which is already default-deny in spirit (quarantine on schema drift until re-approved); (3) it's what makes `tools/list` filtering meaningful — hiding unauthorized tools only matters if "unauthorized" is the default, not the exception; (4) it's what enterprise security review expects as table stakes. **Bootstrap exception:** the first admin account gets implicit access to the *management* API (nodes/policy/users) at setup — default-deny governs MCP *resource* access for every group thereafter, not the admin's own provisioning step.
- **2026-08-03 — Data plane is customer-infrastructure-only, in every tier, no exception.** See the 5th non-negotiable in §0. Reasons stated directly by the founder: trust (no customer will let a third party route their live internal MCP traffic) and cost (Spidercob shouldn't carry the liability/uptime burden of being inline on every customer's production path). This resolves how Mode C registration works: the SaaS control plane (post-funding) only authors policy and pushes signed bundles down a tunnel to a customer-owned container — it is never itself in the request path.
- **2026-08-04 — Policy conflict resolution: deny-overrides-allow, additive-allow across group memberships, default-deny as the base case.** Same evaluation order as AWS IAM: collect every matching rule across all of a principal's groups for a given node/method/tool → any explicit DENY wins → else any explicit ALLOW wins → else (nothing matches) → default-deny. Requires the policy schema to support explicit DENY rules, not allow-only — needed to express carve-outs ("all Jira tools except `delete_ticket`") without enumerating every other tool individually.
- **2026-08-04 — NHI credentialing: two tiers, decoupled from human Mode A/B.** See §1. Tier 1 (v1): static hashed client secret + `client_credentials` grant, for ephemeral/stateless NHIs (CI jobs, serverless — nowhere durable to hold a private key between runs). Tier 2 (v1.1): locally-generated keypair enrolled via the same burnable-token mechanism as gateway container enrollment, for long-running NHIs — no long-lived shared secret ever transmitted. `agent_groups` (already in the §8 data model) gives NHIs their own group membership, independent of the human who registered them — inheriting the owner's access would violate least-privilege for exactly the identities that need it most.
- **2026-08-04 — Continuous auth = short-TTL + fresh re-evaluation on reissuance, no separate polling loop.** Group membership and policy are already re-resolved from the local store on every token reissuance and re-checked per request (§5's "request-time check wins" already implied this) — short access-token TTLs are sufficient; no need for a live "is this token still good" side-channel.
- **2026-08-04 — Force-sync from the control plane is the break-glass mechanism, for Mode C only.** If a customer's local policy store is corrupted, wiping and re-pulling the last-known-good signed bundle from the control plane recovers it — but only for tenants actually connected to one. A disconnected, pure self-hosted deployment (Mode A/B, no control plane) has no such recovery path yet — see §7.
- **2026-08-04 — HA/multi-replica mechanism: independent local SQLite per replica, kept in sync by replaying the same signed policy bundle to each — not a shared database.** SQLite is single-writer; replicas can't safely share one file. Since policy config is small, admin-authored, and already control-plane-durable in Mode C, replicating it to N independently-functional replicas (the same mechanism as container enrollment/first-sync) sidesteps needing Postgres for redundancy in that topology. Consequence: losing a replica doesn't lose *policy* (it's just a mirror, trivially regenerated) — but it does lose that replica's local *audit log* unless audit records are already being streamed continuously to the customer's SIEM or the control plane's metadata aggregation. For HA deployments, local SQLite audit storage should be treated as a short-term buffer, not the system of record.
- **2026-08-04 — Round robin is safe for token *validation*, not safe (alone) for `jti` revocation consistency or MCP session continuity.** Access-token validation is stateless (signed JWT + replicated signing keys) — any replica can verify any token, no affinity needed. But `jti` revocation is currently an in-memory-per-process denylist (design doc §4) — a token revoked on replica A is still valid on replica B unless the denylist is shared. Separately, MCP's own stateful session (the `initialize` handshake + ongoing session mapping, §6) lives in whichever replica's memory established it — a fresh token doesn't fix a request landing on a replica that's never heard of that session. See §7 for the fix options.
- **2026-08-04 — HA/routing infrastructure is entirely the customer's responsibility**, consistent with the data-plane-customer-only non-negotiable. Spidercob provides the mechanism (health endpoints, enrollment, policy replication) — the customer provisions and operates the load balancer, replica count, and routing.
- **2026-08-04 — No separate refresh-token grant; short TTL + re-exchange on expiry is the whole mechanism.** NHI (120s default TTL) re-calls `/token` with the same `client_credentials`; Mode A humans silently re-mint via their local UI session; Mode B humans silently redo the RFC 8693+7523 exchange (invisible under EMA's zero-touch model). This is simpler than a dedicated `offline_access` refresh token *and* naturally keeps the IdP in the loop on every reissuance, directly bounding deprovisioning staleness. Default TTLs: 120s NHI, 10min human, both admin-configurable. `design.md` §4's `offline_access` refresh-token line is superseded by this.
- **2026-08-04 — Policy stub is `DenyAll`, never `AllowAll`, from the moment real tokens exist.** Closes the Phase 2→3 interim-state hazard where a JIT-provisioned, zero-group user would otherwise get full access via a permissive stub. Phase 3 replaces `DenyAll` with the real evaluator; it never replaces a permissive default.
- **2026-08-04 — Okta interop moves into Phase 2, not the Phase 4 launch gate.** A free Okta Developer account (Integrator Free Plan) supports Cross App Access setup — confirmed, no cost blocker. Keycloak alone doesn't exercise Claude Code's actual client-side EMA behavior, which is proven against Okta specifically; catching integration bugs during Phase 2 matches the stated "interop bugs found early are design fixes" principle better than deferring to launch.
- **2026-08-04 — stdio nodes are out of scope for multi-replica HA.** Pinned to whichever single instance spawned them; v1.1 HA covers HTTP-transport nodes only. Building inter-replica stdio ownership/failover would require the same risky node-to-node coordination the control-plane-only distribution model exists to avoid — not worth it. A customer wanting HA for a stdio-backed server should wrap it as a networked HTTP server instead.
- **2026-08-04 — stdio process supervision: restart with exponential backoff, quarantine after repeated crash-looping, fail in-flight sessions cleanly.** Standard pattern (systemd/Kubernetes/supervisord), not invented here. Non-JSON-RPC stdout output is a spec violation by the upstream (MCP requires protocol-only stdout, everything else to stderr) — log as a warning, don't crash the gateway over one bad line, but count repeated violations toward the same quarantine threshold as crashes.
- **2026-08-04 — Rate-limit/quota enforcement is per-replica under HA, accepted as a v1 limitation.** Falls directly out of the no-shared-store-by-default HA decision, not a separate choice. Fine because it's defense-in-depth, not the primary access-control mechanism (policy allow/deny stays exact regardless of replica); exact global enforcement is available later via the same optional shared-store upgrade path as `jti`/session consistency.
- **2026-08-04 — Tool-pin drift detection is a periodic background refresh (admin-configurable interval), not per-request diffing.** Keeps the hot path fast; bounded, known-window drift detection is an acceptable and simpler tradeoff than continuous checking.
- **2026-08-04 — `tools/list` pagination: cursor stays fully opaque, filtered pages (even empty ones) are spec-legal.** No pagination math to reimplement — just filter the `tools` array per page and pass the upstream's cursor through unchanged. Auto-advancing through empty filtered pages is optional future UX polish, not a v1 requirement.
- **2026-08-04 — External security review scope is five seams, not four: added NHI credential issuance (`client_credentials`) alongside token validation, policy evaluation, session mapping, redaction ordering.** The underlying token-signing code is shared with ID-JAG handling, but `client_credentials` authentication logic (e.g., timing-safe secret comparison) is distinct and shouldn't be assumed covered by testing the ID-JAG path alone.
- **2026-08-04 — Sticky LB routing is the default v1.1 HA mechanism, not shared Redis.** Every major cloud LB (AWS ALB, GCP HTTP(S) LB, Azure Application Gateway) and common self-hosted options (nginx, HAProxy, k8s ingress) support session affinity, so this doesn't require customers to adopt new infrastructure. One nuance: MCP's session ID travels as the `Mcp-Session-Id` HTTP header, but most cloud-native LBs' built-in stickiness keys on cookies, not arbitrary headers — so the gateway will also set a mirrored session cookie (same value as the header) on `initialize` responses, purely so native cookie-based LB stickiness works out of the box without customers hand-configuring header hashing. A shared store (Redis, or Postgres if a customer's already running it for HA) remains an available upgrade path later for true any-replica-handles-any-request semantics — not required for the v1.1 default.

- **2026-08-06 — design.md synced to current decisions; treat mismatches as bugs, not alternate truth.** A review pass found design.md's original text still stated the pre-decision TTL range, the `offline_access` refresh design, "four" seams, and an allow-only `policies` schema with no rate-limit column — all superseded since. design.md now carries inline "Updated 2026-08-06" notes at each spot rather than being silently rewritten, so the history of *why* it changed stays visible. The Mode C enrollment/registration mechanism (burnable token → locally-generated keypair → tool-discovery-gated-on-connection) was designed in conversation earlier but had never been written into either doc until this pass — see §1.
- **2026-08-06 — Three engineering risks surfaced by the same review, moved to §7 rather than left implicit:** SQLite write-concurrency configuration, the unverified <5ms latency budget, and Okta's lack of an obvious CI story. None are blockers, all need a conscious decision before the phase that depends on them, not an optimistic default.

- **2026-08-06 — Phase 1 build order resequenced: minimal stdio proxying pulled forward, ahead of session mapping and idle timeout.** The published spec (GitHub issue #1) designs its primary test seam around a `Gateway` configured with *both* an HTTP node and a stdio node together — building strictly in the original flat-list order (session mapping fully done HTTP-only, stdio bolted on after) would mean marking session mapping "done" before its own test design could actually run, then reworking those tests once stdio landed. Full stdio *process supervision* (crash backoff/quarantine) stays last, since it benefits from a real session-teardown path already existing to hook into.
- **2026-08-07 — OAuth AS library: hand-rolled `internal/authserver`, not `ory/fosite` or `zitadel/oidc` v3.** Both frameworks are built around the standard grant catalog (authorization_code, refresh_token, etc.); this gateway's actual surface is two non-standard grants — an internal "re-present your local session" exchange for Mode A humans (not a spec OAuth grant at all) and `client_credentials` for NHIs — plus JWKS and RFC 9728 metadata, with refresh tokens explicitly rejected by an earlier decision (§6, 2026-08-04). Fighting a full AS framework's assumptions about grant shape for a surface this narrow costs more than it saves. Token construction/verification itself still uses a vetted library (`golang-jwt/jwt/v5`, EdDSA/Ed25519 support) rather than hand-rolled JWT encoding — the AS *orchestration* is bespoke, the cryptographic primitive is not. Revisit only if Phase 2b's real RFC 7523/8693 exchange against Keycloak/Okta turns out to need more spec machinery than this seam provides.
- **2026-08-07 — SQLite migrations: hand-rolled embedded-`.sql` runner, not `golang-migrate`.** `golang-migrate`'s sqlite driver depends on `mattn/go-sqlite3` (cgo); this repo already committed to `modernc.org/sqlite` (no cgo) for `internal/store`, and running two different SQLite drivers in one binary just for migrations isn't worth the dependency weight or the risk of the two drivers disagreeing on file locking. Instead: numbered `.sql` files under `internal/store/migrations/`, embedded via `go:embed`, applied in order inside a transaction, tracked in a `schema_migrations` table so a migration never reapplies. Small enough surface (six tables, no branching migration graph) that a real migration framework buys little here.
- **2026-08-07 — JWKS fetch/cache/rotation for external IdPs: `github.com/MicahParks/keyfunc/v3`, not hand-rolled.** Same reasoning as the AS-library and JWT-library decisions above, applied to a different seam: reconstructing RSA/EC public keys from a remote, third-party-controlled JWKS endpoint is exactly the kind of security-sensitive plumbing (MASTER_PLAN's five security-review seams explicitly include token validation) that a hand-rolled implementation risks getting subtly wrong, with no differentiation upside for having written it in-house. `internal/idptrust` owns only the gateway-specific logic (trust-list membership, expected-audience matching) built on top of it.
- **2026-08-07 — Keycloak standard token exchange's `audience` parameter names a registered client, not a URI (real interop finding, `automation/run-e2e-idjag.sh`).** Unlike this gateway's own access tokens (`aud` = a node's canonical URI, RFC 8707-style), Keycloak's audience-scoping convention is a client_id local to the realm. `internal/idptrust.TrustedIssuer.ExpectedAudience` is deliberately just an opaque string match with no assumed shape, precisely so this per-IdP convention difference doesn't leak into the gateway's own validation code — it's a config-time concern for whoever sets up `config.TrustedIdPs`, documented in `interop/README.md`. Getting a client to actually appear in another client's token `aud` required a client-level Audience protocol mapper (`oidc-audience-mapper`); Keycloak's documented alternative (a shared client-scope carrying a role-scope-mapping to the target client's roles) did not reliably apply under the direct-grant flow in practice — recorded here rather than left as a mystery the next person re-discovers.
- **2026-08-07 — `requested_token_type=urn:ietf:params:oauth:token-type:id-jag` is not honored by current Keycloak (26.7.1) — treated as a soft-fail with fallback, not a blocker.** The harness still requests it first (in case a future Keycloak version adds support, at zero cost to check), then falls back to a plain audience-scoped token-exchange when Keycloak returns `"requested_token_type unsupported"`. This is functionally fine: `internal/idptrust.Validate` never inspects an assertion's own type label, only its signature/`iss`/`aud`/`exp`/`jti`, so a "plain" access-token-typed assertion serves exactly the same role as a literally-labeled ID-JAG for this gateway's purposes.
- **2026-08-07 — Phase 3 split into 3a/3b/3c for reviewability, not infrastructure reasons.** Unlike the Phase 2a/2b split (genuinely different test infra, Docker vs. not), all three Phase 3 sub-items are pure-Go and `httptest`-testable — the split here is purely about not bundling a policy engine, a rug-pull defense mechanism, and a scanner rewrite into one issue/PR. See §3.
- **2026-08-07 — `internal/policy`'s `Engine` interface was redesigned, not just reimplemented: `Allow(node, r) bool` → `Decide(ctx, principal, node, method, tool) Decision` + `FilterTools(...)`.** The old boolean, node-only shape couldn't express method/tool-level decisions or return enough for `tools/list` response filtering — this was a genuine interface change (issue #7's seam-check with the user before the spec was written), not an internal detail. A direct consequence: the policy check in `internal/proxy.ServeHTTP` moved to *after* request-body parsing (it needs the JSON-RPC method and, for `tools/call`, the tool name — both only exist post-parse), where it used to run before any body reading happened at all.
- **2026-08-07 — Rate limiting: fixed-window (not sliding), most-restrictive-of-multiple-matching-ALLOW-rules wins.** A simple fixed-window counter per `principal|node` key, injectable clock for testability. When more than one matching ALLOW rule across a principal's groups sets a rate limit, the smallest `max_calls`/`window` pairing applies — consistent with "deny-overrides-allow" already erring toward the more restrictive outcome when rules disagree. `block_on_scan_flag` uses the opposite polarity deliberately: if *any* matching ALLOW rule requests it, it applies — escalating a flag to a block too eagerly is the safe direction, unlike rate limits where the safe direction is the tighter cap.
- **2026-08-07 — `config.Policies` fully replaces the store's `policies` table on every startup; `config.SeedAgents`/`config.TrustedIdPs` do not replace their identity/trust data the same way.** Policy has no independent state of its own beyond config in this phase — no admin API has ever written a policy row that didn't originate from config, so treating config as the complete desired state and reapplying it fresh is simpler and strictly safer than diffing. Identity data (users, agent credentials) is different in kind: it accumulates real state (a generated secret, a login history) that must never be silently wiped just because a restart happened to run with a slightly different config file present.
- **2026-08-07 — `Gateway.SetPolicy`, an exported post-construction setter, not a `New()` constructor parameter, for wiring in the real evaluator.** `internal/proxy.New` still only takes `(cfg, authn)` — every existing call site (five in `proxy_test.go` alone) keeps working unchanged. `cmd/spidercob` calls `gw.SetPolicy(policy.NewEvaluator(db))` once, right after `New`, specifically because the real evaluator needs a `store.Store` that doesn't exist yet at the point `New` itself would need to decide a default. `DevAllowAllPolicy` still wins outright when set — `main.go` only calls `SetPolicy` when it's false, so the existing dev/CI escape hatch (`automation/run-e2e.sh`) can't be silently overridden by whatever real policy config also happens to be present.
- **2026-08-07 — Tool pins use TOFU (trust-on-first-observation), not an admin-approval queue, because no approval mechanism exists yet (issue #9's seam-check with the user, before the spec was written).** Same model SSH host keys and TLS certificate pinning use. The alternative — require an admin to explicitly approve each tool before it's ever callable — would need a real admin API/UI this repo doesn't have until Phase 4; TOFU gets the rug-pull defense live now, at the honest cost that the *very first* observation of any tool is trusted unconditionally. This is the same posture default-deny-with-config-bootstrap already takes elsewhere (§6, 2026-08-03's default-deny entry) — ship the mechanism now, let the admin UI make it fully operator-controlled later.
- **2026-08-07 — Tool pins (and quarantine state) must survive a gateway restart unchanged — re-establishing TOFU on every boot would make the whole defense trivially bypassable.** An attacker who can trigger or wait for a restart would otherwise get a fresh, unconditionally-trusted baseline for a tool they'd already mutated. `internal/store`'s `tool_pins` table is therefore the opposite of `policies` (§6, 2026-08-07 entry above): `policies` is fully replaced from config on every startup because it has no independent state of its own; `tool_pins` is *never* replaced or reset by config or by a restart — a pin is real accumulated state (a trust decision made at a point in time) in exactly the same sense a user's password hash is, not a config mirror.
- **2026-08-07 — One combined hash over name+description+inputSchema, not separate per-field hash columns (`tool_pins.hash`, singular).** design.md's original `tool_pins` sketch (§8) had separate schema/description hash columns; issue #9's spec simplified to one combined hash covering all three fields together. Simpler to reason about and store, and equally effective at catching a change to *any* of the three — nothing in the drift-detection story needs to know *which* field changed, only that something did (`drift_detail` still records the actual old/new hash for investigation, story 12).
- **2026-08-07 — Quarantine is scoped per-tool, keyed on `(node, tool_name)`, never per-node.** A node offering ten tools where one gets mutated should keep the other nine fully usable — collapsing quarantine to node-granularity would make one compromised tool an effective denial-of-service against every legitimate tool on the same server, which is a strictly worse outcome than the rug-pull it's defending against.
- **2026-08-07 — Pin/quarantine checks are fail-static (a store lookup error is treated as "quarantined" for `IsQuarantined`, "drop it" for `NonQuarantined`), matching `policy.Evaluator`'s existing "never fail open" posture, not a new decision invented for this issue.** A pin-registry error must never look identical to "this tool is trusted" — the same reasoning that made `policy.Evaluator.Decide` return `Allowed: false` on any store error (§6/design doc) applies unchanged here.
- **2026-08-07 — The background pin refresher opens its own short-lived upstream connection per refresh (via the existing `newUpstream` machinery), reused for exactly one `initialize`+`tools/list` round trip, then torn down immediately — never registered in `Gateway`'s client-facing session table.** Satisfies story 10 (drift detection must never depend on or interfere with a real client's in-flight session) without adding a parallel "internal session" concept to `session.go`: reusing `newUpstream` (the same seam `handleNewSession` uses) means stdio and streamable_http nodes get identical treatment for free, and skipping session-table registration means the idle-session reaper, any future session-count limit, and session-list/audit views never need to know these ephemeral fetches happened at all.
- **2026-08-07 — `internal/pin.Scheduler`'s background loop is a fixed-cadence ticker (`config.PinCheckIntervalSeconds`, independent of and normally much shorter than any node's own refresh interval) that re-checks per-node due-ness on every tick, not one ticker per node.** Mirrors the idle-session reaper's existing single-ticker-does-the-checking shape (`internal/proxy`) rather than introducing N independent goroutines for N nodes — the actual per-node scheduling decision (`dueForRefresh`, a pure function of `lastRun`/`interval`/`now`) is what's independent per node, not the underlying wake-up mechanism. One node's fetch failure is logged and skipped for that cycle only (story 11) — it does not quarantine that node's tools and does not delay or block any other node's refresh (story 21), since each node's due-check and fetch happen independently within the same `RunOnce` pass.
- **2026-08-07 — `tool_pins` gained a nullable `input_schema` column mid-implementation of issue #11, not anticipated at spec time.** The spec described schema enforcement reading "the pinned inputSchema" via a `Registry` accessor, without spelling out that `tool_pins` (issue #9) only ever stored a *hash* of name+description+inputSchema — a hash can't be un-hashed back into the schema bytes validation actually needs. Storing the raw schema alongside its hash is the minimal fix: the hash still drives drift detection unchanged, the new column exists purely so schema enforcement has something to validate against. NULL means no `inputSchema` was ever pinned (a tool that legitimately takes no structured arguments) — distinct from an empty-but-present schema, same "nil vs. present-but-empty" care already taken for `quarantined_at`/`drift_detail`.
- **2026-08-07 — Schema enforcement is a third, independent `tools/call`-gate check (policy → quarantine → schema), not folded into either existing check.** All three answer genuinely different questions — "is this principal allowed" (policy), "is this still the tool everyone agreed to" (quarantine), "does this specific call's arguments match what was agreed to" (schema) — and issue #9 already established the precedent (story 24) that independent gates should stay distinguishable in their rejection reason, not collapse into one generic "forbidden."
- **2026-08-07 — `google/jsonschema-go` for schema validation, not hand-rolled JSON Schema parsing.** Already an indirect dependency (the MCP go-sdk itself uses it internally for `mcp.AddTool`'s automatic `inputSchema` inference from Go types) — promoted to direct rather than adding a second JSON Schema implementation or writing one from scratch. Same "vetted library for security-sensitive parsing" posture as `golang-jwt/jwt` and `keyfunc` (§6, earlier 2026-08-07 entries).
- **2026-08-07 — `Default()`'s scanner order is `SecretScanner` → `PIIScanner` → `EntropyScanner` → `InjectionScanner`, deliberately, not incidental.** `Chain.ScanResponse` threads each scanner's output into the next, so a value the first two scanners already redacted is structurally gone from the body `EntropyScanner` sees — no cross-scanner "have I already been flagged" bookkeeping needed, ordering alone prevents double-reporting the same secret under two different scanner names (issue #11 stories 26-27).
- **2026-08-07 — SSN and Luhn-valid credit-card detection are unconditional (always redact); email/phone detection is off by default, config-gated, flag-only when enabled.** Different confidence levels call for different defaults: a Luhn-valid number or a structurally-plausible SSN (area/group/serial range-filtered) is specific enough to redact safely; an email or phone number appearing in a tool response is the *common, often-legitimate* case (a CRM/support tool doing its job), per design doc §7's own "often legitimate" framing — redacting those by default would break real workflows, so the honest default is off, and even opted-in, Flag rather than Redact.
- **2026-08-07 — Homoglyph/zero-width normalization is scoped to `InjectionScanner` only, not applied to `SecretScanner`/`PIIScanner` pattern matching.** Design doc §7 places this specifically under injection heuristics. Extending it to secret/PII redaction would require redacting against a normalized copy while mapping the redaction back onto the *original* bytes' positions — a materially harder problem (normalization can change string length, e.g. stripping zero-width characters) that isn't needed for the actual threat model: evading a credential *pattern* match by homoglyph substitution doesn't make sense (an attacker leaking a real secret has no reason to obfuscate it that way), while evading an *injection phrase* match by homoglyph substitution is a real, motivated attack.

- **2026-08-08 — Gateway admin API auth reuses spider-snoop's existing login (NHI service trust + live introspection), not a new gateway login system.** Since spidercob-gateway and spider-snoop launch together as one product, a spider-snoop admin should be able to configure the gateway without a second login. Spider-snoop's own JWT (`python-jose`, HS256, shared-secret-signed, no JWKS) doesn't fit this repo's existing Mode B/`internal/idptrust` trust mechanism directly (that expects an asymmetric-signed, JWKS-published issuer) — rather than sharing spider-snoop's `SECRET_KEY` (real option, rejected: silently misses a spider-snoop logout until the token's own ≤30min expiry) or waiting on a spider-snoop-side revamp to publish JWKS (real option, deferred: cross-repo work with no gateway-side payoff until it lands), the chosen design never asks the gateway to verify spider-snoop's JWT signature at all. Instead: (1) spider-snoop's backend authenticates to the gateway as a designated NHI via the *existing* `client_credentials` grant, scoped to a new reserved `_admin` token audience only that agent may mint (a new mint-time allowlist restriction — ordinary per-node tokens stay open to any authenticated agent, since policy enforcement there happens downstream, not at mint time); (2) the specific human behind each request is verified via a live call to spider-snoop's own already-existing `GET /api/users/me`, the same check spider-snoop's own frontend already relies on. Both zero spider-snoop-side changes to ship the gateway half, and immediate (not TTL-bounded) revocation respect. Full spec: issue #13.
- **2026-08-08 — A standalone shared login/tenant-management service (serving both spider-snoop and the gateway) was proposed and explicitly deferred, not rejected.** Real multi-repo initiative — own repo, own data model, a real existing-admin migration story — that shouldn't be scoped as a side effect of one gateway issue. Issue #13's `SpiderSnoopIntrospector` interface is deliberately the seam that would make adopting one later a config/adapter swap (point introspection at the new service's equivalent endpoint) rather than a gateway rewrite.
- **2026-08-08 — Local Mode A human user management stays out of the admin API for now.** In the spider-snoop-integrated deployment (the one actually being launched), spider-snoop already is the human identity source — a gateway-local `users` CRUD surface would be redundant. Revisit only if/when a pure self-hosted (no spider-snoop) deployment needs it; the original design doc's own "self-hosted OSS, no IAM department" framing assumed no spider-snoop integration existed yet.
- **2026-08-08 — `store.DeleteGroup` explicitly checks for referencing policy rows and refuses (`ErrConflict`) rather than relying on `policies.group_id`'s own `ON DELETE CASCADE`.** The schema-level cascade (issue #7) would make a raw `DELETE FROM groups` succeed by silently wiping every policy row that referenced it too — a group deletion quietly discarding an admin's configured allow/deny rules is exactly the "dangling, confusing policy state" issue #13 exists to prevent, so this operation deliberately overrides the default cascade with an explicit pre-check instead of trusting it.
- **2026-08-08 — Group membership in the admin API is addressed by username/client_id, not the store's internal numeric IDs.** An external caller (spider-snoop's backend, or eventually a human via the UI) naturally knows a username or client_id, never a database row ID — `internal/adminapi` resolves the identifier to an ID internally (`resolveMemberID`) rather than exposing IDs as part of the API's own contract.
- **2026-08-08 — `internal/adminapi`'s `Routes()` uses Go 1.22+'s method- and path-parameter-aware `http.ServeMux` patterns (`"POST /admin/agents"`, `r.PathValue("name")`), the first place in this codebase to do so.** Every prior handler (`/token`, `/mcp/`, RFC 9728 metadata) either had a fixed path or did its own prefix-stripping, because none of them needed more than that. `internal/adminapi` has eight genuinely path-parameterized REST routes (a group name, a client_id, a membership type+identifier) where manual string parsing would be more error-prone than the tool built for exactly this.
- **2026-08-08 — `CachingIntrospector` never caches an introspection error, only a success.** A transient spider-snoop blip must not keep denying admin access for the whole cache TTL once spider-snoop recovers — an error always retries live on the very next request, while a successful "yes, admin" result is cached briefly (default 30s) to avoid a live network call on every single admin request in a burst.
- **2026-08-08 — `AuthenticateAgent` (`internal/identity`) rejects a revoked agent's otherwise-correct secret identically to a wrong one, not as a distinguishable error.** Revocation existing must never be probeable via the error shape — the same non-enumeration property this function already guaranteed for unknown-client_id vs. wrong-secret before issue #13 added revocation as a third case.

- **2026-08-08 — Nodes are currently baked into three separate, independently-built, write-once-at-construction node registries — discovered during issue #15's seam-check, not previously documented.** `proxy.Gateway.nodes`, `authserver.AuthServer.nodes`, and `pin.Scheduler`'s node list are each built once, from `cfg.Nodes`, at their respective `New()`/construction call, and never touched again. This is why "node registration" can't just mean "add a store table and an admin endpoint" the way agents/groups/policies (issue #13) could — those were already store-backed and looked up live on every request, so an admin-API write took effect immediately; nodes aren't looked up per-request at all today, for routing-performance/simplicity reasons. Issue #15 sidesteps rebuilding all three as live structures by having `cmd/spidercob` read the *complete* current node set (`store.ListNodes()`, config-sourced rows upserted into the same table on every startup) once, before any of the three constructors run — zero changes inside `internal/proxy`/`internal/authserver`/`internal/pin` themselves, but also, deliberately, no hot-reload: a node still needs a restart to become routable. True hot-reload (making all three registries live-updatable, almost certainly needing a mutex or `sync.Map` around what are today plain maps) is scoped as a separate, later issue once this persistence layer exists to build it on.

- **2026-08-08 — The admin UI ships gateway-embedded (`go:embed`, cookie-based browser session) rather than living in spider-snoop or having the gateway self-mint its own NHI token (issue #17's seam-check, before the spec was written).** Three real options were on the table. (1) *Chosen:* the UI ships in this repo, and a new, strictly additive cookie-based session — minted from a one-time live-introspection check via the *same* `SpiderSnoopIntrospector` the service-to-service path already uses — lets a browser authenticate without ever holding the NHI `client_secret` that mechanism requires. (2) *Rejected:* the UI lives in spider-snoop instead, which already holds both the NHI secret and the live human session server-side, and would need zero new gateway-side auth surface at all — rejected because it would mean this repo's job stops being "a real, usable HTTP backend" and starts depending on spider-snoop's own frontend release cycle to ever be usable by anyone, undermining the self-hosted-OSS story this product is actually for. (3) *Rejected:* the gateway holds its own admin-integration credential and self-mints its own `_admin` token server-side, using the cookie purely to prove the human's session — rejected as needlessly indirect (the gateway ends up being its own "trusted integration client," a role that only makes sense for an external caller) once (1) demonstrated the NHI token doesn't need to be involved in the browser path at all. `gateBrowserOrService` (issue #17) keeps this strictly additive: a present-but-invalid-or-missing cookie falls through to the completely unmodified original dual-trust gate, so a caller that never sends a cookie sees byte-identical behavior to before this issue, and the cookie path is deliberately never accepted on `/admin/nodes`.

## 7. Open Decisions (need a call before Phase 2 starts)

- **Final OSS name/trademark/domain check** — still using `spidercob-gateway`; design doc's Phase 0 called for a dedicated check before this locks in publicly.
- **CLA vs DCO** for external contributions — needs deciding before Phase 4 launch gate, not urgent now.
- **Disconnected self-hosted HA/backup story (no control plane at all):** Mode C's replica-recovery-via-policy-replication doesn't apply here — a pure Mode A/B deployment with no control-plane connection needs its own answer (documented SQLite backup, or an export/import CLI) before v1.1 HA claims apply to that topology too. Not designed yet.
- **NHI credentialing build order:** tier 1 (static secret) is proposed to land in Phase 2 alongside human identity; tier 2 (keypair enrollment) is proposed for v1.1. Reasonable default, not yet stress-tested against real NHI use cases.
- **Container lifecycle management vs. policy sync, as separate control-channel concerns.** "Which image version is running / health / restarts" (fleet lifecycle) is a different message type than "here's the current signed policy bundle" (config sync) — keep them as distinct channels/messages on the future control-plane tunnel so a bad policy push and a bad version rollout don't share a rollback path. Not designed yet, relevant to the post-funding Managed tier.
- **The <5ms p50 added-latency budget (design doc §16) is plausible but unverified.** Ed25519 verification and in-memory map lookups are fast enough in isolation, but nothing's been load-tested against realistic payloads — a large `tools/list` response being filtered, or a big tool-call argument being schema-validated and scanned, could plausibly exceed it. Load-test this early in Phase 3 rather than carrying it to launch as an unverified assumption.
- **Okta interop has no CI story yet.** Keycloak runs in a container and is naturally CI-able (already stubbed in `docker-compose.yml`). Okta is a hosted SaaS dev org with no equivalent "spin up fresh per CI run" option — meaning either a persistent dev-org's credentials live as CI secrets (a real secret-hygiene question for this repo's own CI) or Okta interop checks stay manual/pre-release rather than continuous. Undecided; needs settling now that Okta interop moved into Phase 2 (§6, 2026-08-04).
- **The original ~12-week timeline (design doc §13.2) is stale, not confirmed.** Real scope has been added since the original estimate (see the 2026-08-06 note in design.md §13.2) without the timeline being explicitly revisited. Not urgent to fix today, but shouldn't be quoted anywhere (docs, GTM planning) as still holding without a deliberate re-estimate.
- **`make ci-interop` (issue #5) doesn't run in GitHub Actions CI yet.** It needs Docker plus network egress to pull the Keycloak image, neither confirmed available/configured on the self-hosted Hetzner runner. Until this is wired, a Phase 2b-touching PR's `make ci-interop` green run is something the developer/agent ran and reports, not something CI independently re-verified — a real gap, worth closing before this becomes a repeated pattern across more Docker-requiring interop targets (Okta, if it ever gets a CI story per the item above).
- **Phase 3 vs. remaining Phase 2 work ordering.** With Phase 2b done, the original "don't start Phase 3 before an ID-JAG round-trips through Keycloak" gate (§3) is satisfied. Whether to pick up any further Mode B polish (e.g. Okta automation, if its CI story ever resolves) before or interleaved with Phase 3's policy engine is an open sequencing call, not resolved by this doc — Phase 3 is arguably more urgent since `DenyAll{}` currently blocks every identity mode equally from doing anything useful end-to-end.
- **Standalone (no spider-snoop) deployments have no admin surface at all.** Surfaced explicitly during issue #21's seam-check, deliberately not solved there: `internal/adminapi` — and every admin UI screen built on it (issues #17/#19) — is entirely gated on `Config.AdminAPIEnabled()`, which requires spider-snoop integration to be configured. A pure self-hosted deployment (the README's "no IAM department, `docker compose up`" pitch) has no login, no `/admin/*`, nothing beyond `config.json` authoring to manage the gateway with — issue #21's CSV user import works for that deployment shape specifically *because* it's a config-bootstrap mechanism, not because the gap is closed. Needs a real design pass (a local-admin login independent of spider-snoop? a first-run bootstrap flow?) before any admin-API/UI feature can meaningfully target the standalone deployment story again — not urgent for the spider-snoop-integrated launch, but a real gap in the "small team, 15 minutes, no IAM department" pitch as currently built.
