## What this is

Open-source, self-hosted MCP gateway: spec-correct agent identity (ID-JAG / MCP Enterprise-Managed Authorization) plus policy and DLP, in one container, for teams without a dedicated IAM department. Full north star: `MASTER_PLAN.md` §0 on `main`.

## Where things stand (as of 2026-08-08)

- **Phase 3c is done and merged — Phase 3 is now fully complete.** [PR #12](https://github.com/SpiderCob/spidercob-gateway/pull/12) merged to `main`, closing [issue #11](https://github.com/SpiderCob/spidercob-gateway/issues/11) — the last Phase 3 item: schema enforcement, expanded secret/PII detection, entropy scoring, evasion-resistant injection heuristics.
- **Schema enforcement** is a third, independent `tools/call`-gate check (after `policy.Decide`, after `pin.IsQuarantined`): new pure `pin.ValidateArguments(schema, arguments)` using `google/jsonschema-go` (promoted from an indirect to a direct dependency — already pulled in transitively by the MCP go-sdk's own `inputSchema` inference) validates a call's arguments against the tool's pinned schema. No pin yet, or a pin with no `inputSchema`, both skip validation (never blocks) — same "absence isn't evidence of anything" posture `IsQuarantined` already takes. A violation is rejected the same way the scan chain's `Block` action already is, with a message naming "pinned schema" so it's distinguishable from a policy or quarantine denial.
- **This required a real schema change discovered mid-implementation, not anticipated at spec time**: `tool_pins` (issue #9) only ever stored a *hash* of name+description+inputSchema — a hash can't be un-hashed back into the schema bytes validation needs. New nullable `input_schema` column (migration 0005) persists the raw pinned schema alongside its hash; `Registry.PinnedSchema` is the new read accessor.
- **`internal/scan` grew from 2 scanners to 4**, `Default()`'s chain now `SecretScanner → PIIScanner → EntropyScanner → InjectionScanner` (order is deliberate — `Chain.ScanResponse` threads each scanner's output into the next, so a value already redacted by an earlier scanner is gone from the body a later one sees, preventing double-flagging): `SecretScanner` pattern set expanded 5→9 (Azure/Stripe/GitHub/DB-connection-string patterns added); new `EntropyScanner` (Shannon entropy over regex-extracted candidate tokens, flag-only, never redacts); new `PIIScanner` (Luhn-validated credit cards + plausibility-filtered SSN redact by default; email/phone flag-only, off by default, config-gated via new `config.ScanDetectEmail`/`ScanDetectPhone`); `InjectionScanner` now matches against a `normalizeForDetection`-normalized copy (curated homoglyph map + zero-width-codepoint stripping) — detection-only, the real bytes returned/passed through are never altered.
- **`automation/run-e2e-schema.sh`** (new, wired into `make ci`) reuses `run-e2e-pin.sh`'s `pinserver` stdio fixture — its tool's `inputSchema` is the MCP go-sdk's own real, inferred schema (required `text` string, `additionalProperties:false`), not hand-crafted. After TOFU establishment: valid arguments succeed; missing the required field, a wrong-typed field, and an unexpected extra property are each rejected (403, "pinned schema" in the reason) before ever reaching the upstream.
- `make ci` now runs **six** Docker-free layers: `run-tests.sh`, `run-e2e.sh`, `run-e2e-auth.sh`, `run-e2e-policy.sh`, `run-e2e-pin.sh`, `run-e2e-schema.sh`. `make ci-interop` (real Keycloak, Docker-required) is unaffected and still green.
- **`run-e2e-pin.sh`'s own `tools/call` fixtures needed updating** — `pinserver`'s tool now has a real inferred schema requiring a `text` argument, so the pin e2e script's previously-empty `{}` argument payloads would themselves trip schema enforcement for an unrelated reason; fixed to pass `{"text":"hello"}`.
- **Aside, reported back to the user, not part of this repo**: the `dlp-scan` pre-commit hook (separate `spidercob` Claude Code plugin / `dlp-patterns` repo) has a real, now-diagnosed false-positive problem — blocks on any CRITICAL finding regardless of the `context_score` the engine already computes, a `bearer_token` pattern with no length floor, and a bare-English-word `sensitive_keyword` list. User is fixing it in their own DLP pipeline in a separate window; mid-fix as of this session (their local `pre_commit_scan.sh` already shows a diff-scoped, context-score-gated rewrite in progress). Not this repo's concern beyond having hit it on every issue's commit step so far.
