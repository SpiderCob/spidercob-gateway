# Spidercob Gateway — Current State

**Read this first in a new session with no memory of prior conversations.** For the full plan and rationale, see `MASTER_PLAN.md` and `docs/design.md` on `main` — this file is a rolling snapshot, not a replacement for those. It lives on this orphan branch (`context_main`) deliberately, separate from `main`'s code history — nothing to check out here, just a doc to read. See `CLAUDE.md` on `main` for the update procedure and why this is a different thing from any future domain-glossary `CONTEXT.md`.

## What this is

Open-source MCP gateway: spec-correct agent identity (ID-JAG / MCP Enterprise-Managed Authorization) plus policy and DLP, in one container. Launches together with **spider-snoop** (the parent Spidercob product) as one integrated product, not two separate logins. Full north star: `MASTER_PLAN.md` §0 on `main`.

## Where things stand (as of 2026-08-08)

- **Phase 3 is fully complete, and Phase 4's first slice is done and merged.** [PR #14](https://github.com/SpiderCob/spidercob-gateway/pull/14) merged to `main`, closing [issue #13](https://github.com/SpiderCob/spidercob-gateway/issues/13) — a new `internal/adminapi` package: a real HTTP admin API for agents/groups/policies, mounted at `/admin/`.
- **Auth model, decided in conversation before the spec was written (`MASTER_PLAN.md` §6, 2026-08-08):** the gateway does **not** get its own admin login. `/admin/*` is gated by two independent checks, both required: (1) a service-to-service NHI bearer token, minted via the *existing* `/token` `client_credentials` grant scoped to a new reserved `authserver.AdminResource` (`_admin`) audience that only a config-allowlisted agent (`Config.AdminIntegrationClientIDs`) may mint; (2) a live introspection call (`SpiderSnoopIntrospector`) against spider-snoop's own already-existing `GET /api/users/me`, via a new `X-Spidercob-Admin-Session` header, confirming the specific human currently holds an `admin`/`superadmin` role. Both fail-static. Two real alternatives were considered and rejected/deferred: sharing spider-snoop's HS256 `SECRET_KEY` directly (rejected — silently misses a spider-snoop logout for up to its own TTL), and waiting on a spider-snoop-side JWKS revamp to plug into the gateway's existing Mode B/`internal/idptrust` trust path (deferred — real cross-repo work, no payoff until it lands). **Nothing in this issue required a spider-snoop-side change.**
- **A standalone shared login/tenant-management service (serving both products) was proposed and explicitly deferred, not rejected** — real multi-repo initiative with its own migration story, out of scope for this issue. The `SpiderSnoopIntrospector` interface is the seam that would make adopting one later a config swap, not a gateway rewrite.
- **`CachingIntrospector`** wraps the real `HTTPIntrospector` with a short, explicit-TTL cache (default 30s) — errors are never cached, so a spider-snoop blip doesn't keep denying access past recovery.
- **Endpoints**: agents (list/create/revoke — revocation is soft, a new nullable `agents.revoked_at` column, never a hard delete), groups (list/create/delete, membership assign/remove — addressed by username/client_id, not internal DB IDs), policies (list/replace — reuses `store.ReplacePolicies`'s existing semantics, not a second policy-application path). Every successful action is `slog`-logged with both the NHI subject and the human's username/role.
- **New `internal/store` methods**: `ListAgents`, `RevokeAgent`, `ListGroups`, `DeleteGroup` (refuses via `ErrConflict` if any policy still references the group — deliberately overrides the schema's own `ON DELETE CASCADE`, since silently wiping an admin's policy rules on group deletion would be exactly the confusing state this issue exists to prevent), `RemoveUserGroup`/`RemoveAgentGroup`, `AllPolicies` (unfiltered, distinct from the evaluator's scoped `PoliciesForGroups`).
- **`internal/identity.AuthenticateAgent`** now rejects a revoked agent's otherwise-correct secret identically to a wrong one — revocation must never be probeable via the error shape.
- **`automation/run-e2e-adminapi.sh`** (new, wired into `make ci`) proves the whole flow against the real compiled binary: a non-allowlisted agent's admin-token mint attempt is rejected first; then a real `_admin`-audience token plus a real fixture HTTP server (new `internal/adminapi/testdata/fakespidersnoop`, standing in for spider-snoop) drive real admin operations (create agent, create group, assign membership, replace policy) through the full dual-trust gate, with store-visible effects confirmed afterward via the same API.
- `make ci` now runs **seven** Docker-free layers: `run-tests.sh`, `run-e2e.sh`, `run-e2e-auth.sh`, `run-e2e-policy.sh`, `run-e2e-pin.sh`, `run-e2e-schema.sh`, `run-e2e-adminapi.sh`. `make ci-interop` (real Keycloak, Docker-required) is unaffected and still green.
- **`internal/adminapi/routes.go`** is the first place in this codebase using Go 1.22+'s method/path-parameter-aware `http.ServeMux` patterns (`"POST /admin/agents"`, `r.PathValue("name")`) — every prior handler either had a fixed path or did manual prefix-stripping, since none needed more than that; `/admin/*` has eight genuinely path-parameterized REST routes.
- **`dlp-scan` pre-commit-hook false-positive issue** (reported to the user last session) is being fixed on their end in a separate window (diff-scoped + context-score-gated rewrite of `pre_commit_scan.sh`) — this issue's own commit went through cleanly, unblocked, for the first time this session.
