## What this is

Open-source MCP gateway: spec-correct agent identity (ID-JAG / MCP Enterprise-Managed Authorization) plus policy and DLP, in one container. Launches together with **spider-snoop** (the parent Spidercob product) as one integrated product, not two separate logins. Full north star: `MASTER_PLAN.md` §0 on `main`.

**Done, 2026-09-21 — issue #61 (windowed entropy/injection scanning for streamed responses), [PR #62](https://github.com/SpiderCob/spidercob-gateway/pull/62):**
- Closes the one gap issue #55 deliberately left open: a streamed (`text/event-stream`) response got secret/PII redaction via the windowed scan path, but `EntropyScanner`/`InjectionScanner` (flag-only, never redact) stayed buffered-only — a streamed response was a silent blind spot for exactly the two detectors `docs/design.md` §7 calls out as differentiators.
- New `windowedFlagger` (`internal/scan/window.go`) implements `ResponseWindow` for flag-only scanners — "flag once across the whole stream, then passthrough unmodified" — a distinct shape from the redact-in-place windowing `SecretScanner`/`PIIScanner` already had, since these scanners never touch the bytes. All four default scanners now implement `StreamScanner`.
- Detection logic (`injectionResponseMatch`/`entropyMatch`) factored out of the existing buffered-path code so buffered and streamed responses share one implementation — no drift between what gets flagged on each path.
- Real e2e proof (`run-e2e-stream-scan.sh`, extended): a high-entropy token and an injection phrase, each split across a real chunk boundary through a real compiled binary, are flagged exactly once via **exact-value** Prometheus metric checks — a bare substring `check_contains` would still pass a "flag once" regression that double-counted, so the script asserts the literal counter value instead.
- **Real Copilot-review finding on this PR, fixed post-open**: the new exact-value metric checks read a Prometheus line via `grep -F` with no guard, under the script's `set -euo pipefail` — a real regression making the metric line absent would abort the whole script with a raw shell error instead of failing cleanly through the existing `check()` helper. Fixed with `|| true`, the same guard `json_field()` already used for exactly this reason (see next bullet's correction: Copilot's auto-review is evidently back on, contrary to the 2026-08-13 note below).

**Done, 2026-08-30 — issue #59 (`spidercob-admin`: the gateway as its own MCP server, design doc §9.1), [PR #60](https://github.com/SpiderCob/spidercob-gateway/pull/60):**
- The gateway can now be managed by talking to it. A reserved, always-registered node (`spidercob-admin`), reached **in-process** — zero network hop, zero subprocess, via the real go-sdk `mcp.NewStreamableHTTPHandler` wrapping a real `*mcp.Server` — through the exact same policy/pin/scan/audit pipeline every other node already goes through. Default-deny until an operator grants a group access to it, same as any other node; the first grant has to happen through the existing REST admin API, not a bootstrapping problem, just a stated dependency.
- Seven tools: `list_nodes`, `grant_access`, `revoke_access`, `query_audit`, `kill_session`, `list_quarantined_tools`, `approve_tool`. The four mutating ones share one describe-then-`confirm:true` helper — a call without `confirm` performs zero mutation and only describes what would happen, so a prompt-injected agent can't silently escalate through this surface.
- **Two genuinely new backend capabilities that didn't exist anywhere before this issue**: `store.ListQuarantinedToolPins` (a global "what's quarantined anywhere" read) and `store.ApproveToolPin`/`pin.Registry.Approve` (the only way a quarantine ever clears — `Observe` itself still never re-approves anything). `approve_tool` re-fetches the tool's *live* definition before approving; a failed fetch is a real error, never a false "approved."
- **New generic seam in `internal/proxy`, not spidercob-admin-specific**: `inProcessUpstreamSession`, a `sessionUpstream` backed by a plain `http.Handler` (`httptest.Recorder` + a direct `ServeHTTP` call instead of `client.Do`) — reusable if a second in-process node is ever needed. `Gateway.RegisterInProcessNode` is the only way to reach it; no `config.Node` shape can carry an `http.Handler`, so there's no admin-API request path into it at all.
- **Self-review before human review caught a real, security-relevant finding, not a style nit**: a reserved-node-name collision could DoS the admin surface. `POST /admin/nodes {"name":"spidercob-admin",...}` succeeded at the store layer (never a store row on its own, only a live in-process `g.nodes` entry, so no unique-constraint conflict caught it) even though live-apply correctly failed silently; a subsequent `DELETE` then passed `deleteNode`'s `Source==NodeSourceConfig`-only guard and reached `NodeRegistrar.RemoveNode`, tearing down the real, live routing entry. **Two ordinary, already-permitted REST calls, no special privilege, no restart-required — a full DoS of the gateway's own admin MCP surface.** Fixed in two independent layers: `internal/adminapi.createNode` now rejects the reserved name outright before any store write; `proxy.Gateway.AddNode`/`RemoveNode` (issue #57's own methods) now also refuse to shadow or remove an in-process-registered node, as defense in depth. Reproduced for real against the compiled binary before *and* after the fix (not just asserted), and is now a permanent regression check in the e2e script. **Worth remembering**: this is exactly the kind of cross-cutting security gap (name-collision between an admin-manageable resource and a reserved system name) worth checking for again if any *other* reserved name ever gets added to this gateway.
- A real, non-security finding from a manual smoke test before the e2e script existed: the go-sdk's `StreamableHTTPHandler` is spec-strict about `Content-Type: application/json`/`Accept: application/json, text/event-stream` — stricter than the gateway's own hand-rolled JSON-RPC parsing for ordinary nodes, which every *other* e2e script's bare `curl -d` calls get away with. Not a bug; a real MCP client already sends both. If a future e2e script targets `spidercob-admin` directly, remember these headers.
- `automation/run-e2e-spidercob-admin.sh`: 26 checks against the real compiled binary, a real stdio node (`pinserver`, reusing `run-e2e-pin.sh`'s own rug-pull fixture — a real quarantine triggered by actually rewriting the fixture's description mid-run, not simulated), and a real fake spider-snoop.

**Done, 2026-08-30 — issue #55 (windowed streaming/SSE response scanning), [PR #56](https://github.com/SpiderCob/spidercob-gateway/pull/56):**
- Closes the real gap Phase 3c left open: an upstream's `text/event-stream` response used to be fully buffered in memory before scanning and sent in one shot — safe, but not streaming at all, and with no cap on how much a response could grow the process's memory (the request side already had `maxBodyBytes`; the response side had no equivalent). Now a real windowed, boundary-safe scan-and-flush loop relays it incrementally via `http.Flusher`, and a new `defaultMaxStreamBytes` cap terminates a runaway stream.
- `SecretScanner`/`PIIScanner` (the two that already redact unconditionally) implement the pre-existing `StreamScanner` interface for real now; `EntropyScanner`/`InjectionScanner` stay buffered-only, deliberately deferred.
- **A real, separate security bug was found and fixed by this issue's own self-review pass, before human review ever saw it**: `tools/list` responses have no equivalent filtering step in the new streaming path, so an upstream answering `tools/list` via SSE (legal under the MCP streamable_http transport) would have silently bypassed the policy/quarantine tool-visibility filtering issue #7/#9 built. Fixed by routing `tools/list` to the buffered path unconditionally, plus a new `sseEventData` helper that unwraps SSE framing before filtering runs, for the case where the upstream SSE-wraps even a buffered response.
- **A real, unrelated bug also surfaced and got fixed along the way**: `statusRecorder` embedded `http.ResponseWriter` as an interface field, which doesn't promote `Flush()` — every request past a session's first `initialize` would have silently never flushed incrementally, defeating this whole issue's point on the common case.
- Real end-to-end proof against a separate compiled upstream fixture (`internal/proxy/testdata/sseupstream`), not just in-process: a secret split across a real chunk boundary redacted; genuine incrementality proven via time-to-first-byte far below a deliberately long inter-chunk pause; a runaway stream cut off at the cap well before curl's own much longer timeout (`run-e2e-stream-scan.sh`, now in `make ci`).
