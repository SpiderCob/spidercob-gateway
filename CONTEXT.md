# Spidercob Gateway — Current State

**Read this first in a new session with no memory of prior conversations.** For the full plan and rationale, see `MASTER_PLAN.md` and `docs/design.md` on `main` — this file is a rolling snapshot, not a replacement for those. It lives on this orphan branch (`context_main`) deliberately, separate from `main`'s code history — nothing to check out here, just a doc to read. ## What this is

Open-source MCP gateway: spec-correct agent identity (ID-JAG / MCP Enterprise-Managed Authorization) plus policy and DLP, in one container. Launches together with **spider-snoop** (the parent Spidercob product) as one integrated product, not two separate logins. Full north star: `MASTER_PLAN.md` §0 on `main`.

- **Issue #23, what landed — and what it deliberately didn't:**
  - Scoped narrower than `docs/design.md` §6's fuller vision (a hash-chained record for *every* proxied MCP request — `node`/`method`/`tool`/`decision`/`latency`/scanner-verdicts). That's real, separate, later work with its own hot-path latency-budget considerations (the still-open "<5ms p50" decision, `MASTER_PLAN.md` §7) — deliberately deferred at this issue's seam-check, not bundled in as a side effect of unblocking a UI screen.
  - `internal/audit` (new, pure package, no store dependency — mirrors `pin.Hash`/`pin.Drifted`'s exact split): `Record` (deliberately generic actor/action/resource fields, not proxy-request-shaped, so a future per-request-audit issue can reuse the same type without a breaking change), `Hash(prevHash, Record) (string, error)` (SHA-256 over null-byte-separated fields), `Verify([]StoredRecord) error` (walks a chain, recomputes every hash, names the *exact* record index that fails the first time one doesn't — real tamper-evidence, tested against a genuinely corrupted real file, not just a hand-constructed unit-test slice).
  - `internal/store`: new append-only `audit_log` table — **no update or delete method of any shape exists for it anywhere in `store.Store`**, not a convention, an actual absence. `AppendAuditRecord` owns chain-integrity atomicity itself (fetch-last-hash-then-insert inside one transaction, same precedent `ResolveOrCreateExternalUser` already set — a real concurrency test proves many goroutines appending at once still produce one valid, gap-free chain). `ListAuditRecords` exists now specifically so a future query endpoint and the eventual audit-viewer UI screen are both a thin layer on top when they land, not a redesign.
  - `internal/adminapi`: `logAdminAction` — the single, already-isolated call site all nine admin mutations already shared — now also calls `AppendAuditRecord` alongside its existing `slog.Info`, using the identical fields already logged. A store failure there is logged but **never fails the already-succeeded admin request** — a deliberate, explicitly-stated availability-over-strict-consistency tradeoff, not a silent gap for a future reader to discover by surprise.
  - `automation/run-e2e-audit.sh` (new, wired into `make ci`) + two new real fixture programs (`internal/audit/testdata/verifychain`, `.../corruptrow`, since no HTTP endpoint exposes audit records yet): a rejected/unauthenticated request first leaves no record; three real admin operations through the compiled binary leave three real, chained rows, confirmed by `verifychain` opening the actual `store_db_path` directly; then `corruptrow` directly `UPDATE`s one row via raw SQL — bypassing `store.Store`'s append-only interface entirely, simulating real attacker/operator DB access — and `verifychain` confirms verification now fails and names that exact record.
  - **`MASTER_PLAN.md` §3's step list now splits 10c-4 (this issue, the core mechanism, done) from 10c-5 (the audit-viewer UI screen itself, renumbered, still unblocked-but-unspec'd)** — 10c-5 still needs a `GET /admin/audit`-shaped query endpoint that doesn't exist yet before the screen is buildable.
- `make ci` now runs **twelve** Docker-free layers (added `run-e2e-audit.sh`). `make ci-interop` (real Keycloak, Docker-required) is unaffected and still green.

**Secondary, not urgent:** `make ci-interop` still doesn't run in GitHub Actions CI (needs Docker + network egress, unconfirmed on the self-hosted Hetzner runner) — `MASTER_PLAN.md` §7, unresolved across several issues now. The GitHub Actions workflow still runs plain `gofmt`/`go vet`/`go build`/`go test` (no `make web`/npm step) — fine today since `internal/webui/dist`'s tracked `.gitkeep` keeps the Go build green without Node.js, but CI isn't currently proving the frontend actually builds. **Local-dev gotcha, now hit four times (issues #17, #19, #21, #23):** a real `npm run build` (Vite's `emptyOutDir: true`) wipes the tracked `internal/webui/dist/.gitkeep` placeholder — `git status` shows it deleted after building the frontend locally, or after running `make ci`/`make web` at all (they both depend on `make web`); `touch` it back before committing.
