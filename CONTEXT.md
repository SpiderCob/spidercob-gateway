# Spidercob Gateway — Current State

**Read this first in a new session with no memory of prior conversations.** For the full plan and rationale, see `MASTER_PLAN.md` and `docs/design.md` on `main` — this file is a rolling snapshot, not a replacement for those. It lives on this orphan branch (`context_main`) deliberately, separate from `main`'s code history — nothing to check out here, just a doc to read. See `CLAUDE.md` on `main` for the update procedure and why this is a different thing from any future domain-glossary `CONTEXT.md`.

## What this is

Open-source MCP gateway: spec-correct agent identity (ID-JAG / MCP Enterprise-Managed Authorization) plus policy and DLP, in one container. Launches together with **spider-snoop** (the parent Spidercob product) as one integrated product, not two separate logins. Full north star: `MASTER_PLAN.md` §0 on `main`.

## Where things stand (as of 2026-08-08)

- **Phase 3 is fully complete, and Phase 4's first three slices are done and merged.** [PR #14](https://github.com/SpiderCob/spidercob-gateway/pull/14) (issue #13) shipped the admin API backend. [PR #16](https://github.com/SpiderCob/spidercob-gateway/pull/16) (issue #15) shipped node registration. [PR #18](https://github.com/SpiderCob/spidercob-gateway/pull/18) just merged, closing [issue #17](https://github.com/SpiderCob/spidercob-gateway/issues/17) — the admin UI's first real screen: agents/groups/policies, manageable from a browser.
- **Issue #17, what landed:**
  - **The core problem it solved:** issue #13's dual-trust gate (NHI-audience-restricted `client_credentials` token + live spider-snoop introspection) was built for *service-to-service* callers holding an NHI `client_secret`. A browser can never safely hold that secret, so the UI needed a second, browser-appropriate trust path — additive, not a weakening of the existing one.
  - `internal/uisession` (new package): an in-memory browser session registry (same precedent as MCP's own `Mcp-Session-Id` mapping — not store-backed, a restart logs every UI session out). `Valid(session, now, maxAge) bool` is the pure decision function, mirroring `pin.dueForRefresh`'s injectable-clock pattern. `RegistryConfig`'s exported `Clock` field mirrors `pin.SchedulerConfig`'s pattern specifically so `internal/adminapi`'s own tests can control expiry timing cross-package.
  - `internal/adminapi`: new `POST/GET/DELETE /admin/ui/session` (login/whoami/logout). Login verifies a submitted spider-snoop session token via the *same* `SpiderSnoopIntrospector` the service-to-service path already uses (zero new spider-snoop-side surface) and mints a `uisession`, set as an `HttpOnly`/`SameSite=Strict` cookie. `gateBrowserOrService` tries a present cookie first — re-introspecting its underlying spider-snoop token *live*, on every request, never just a registry hit — and falls through to the completely unmodified original dual-trust gate otherwise, so every pre-existing NHI-token-plus-header test still passes byte-for-byte unchanged. The cookie path is wired onto agents/groups/policies only — deliberately never `/admin/nodes`, which stays service-to-service only.
  - `internal/config`: new `AdminUISessionMaxAgeSeconds` (default 8h), bounding a UI session's total lifetime independent of the live per-request introspection re-check.
  - `web/` (new): the **first frontend code in this repo** — React + Vite + TypeScript, no router library or UI kit (kept deliberately minimal, three screens). Login (manual paste of the spider-snoop session token — the one deliberately unpolished piece of this v0; no redirect-based SSO yet, that's real spider-snoop-side work, explicitly deferred), Agents (list/create/revoke, one-time secret display), Groups (list/create/delete, membership add/remove), Policies (list + a structured replace form, warns before a save that would drop an existing rule).
  - `internal/webui` (new package): embeds and serves the built UI at `/ui/` via `go:embed` — the second use of `go:embed` in this repo, after `internal/store/migrate.go`'s migrations. Build output physically lives at `internal/webui/dist`, **not** `web/dist` — `go:embed` can't reach across a `../` pattern, so the Go package doing the embedding has to contain its own build output. `dist/` is gitignored except a tracked `.gitkeep` placeholder, so a fresh clone's `go build`/`go vet`/`go test ./...` all still succeed with zero Node.js installed (serving 404s under `/ui/` until a real `npm run build` runs) — verified directly against a fresh clone of the merged branch before opening the PR. `make build`/`make ci` both gained a new `make web` dependency (`cd web && npm ci && npm run build`) so the default path always produces a real, UI-serving binary.
  - `automation/run-e2e-adminui-session.sh` (new, wired into `make ci`): a real curl cookie jar (never an NHI bearer token) logs in against the real compiled binary and drives real agent/group/policy create/list/delete operations — confirmed rejected on `/admin/nodes` — while the pre-existing service-to-service path is proven completely unaffected; also proves logout actually invalidates the cookie, and that a session expires on its own past a deliberately short configured max age (2s + a real sleep, same pattern `run-e2e-auth.sh` already uses for token-TTL expiry), without an explicit logout.
  - **Architecture decision, recorded in `MASTER_PLAN.md`'s decisions log:** three real options for where the UI's auth surface should live were weighed before the spec was written — gateway-embedded UI with a cookie-based BFF (**chosen**), the UI living in spider-snoop instead (rejected — would make this repo's own admin surface depend on spider-snoop's frontend release cycle, undermining the self-hosted-OSS story), and the gateway self-minting its own NHI token server-side (rejected — needless indirection once the cookie approach showed the NHI token doesn't need to touch the browser path at all).
- `make ci` now runs **nine** Docker-free layers (added `run-e2e-adminui-session.sh`) and now depends on `make web` first. `make ci-interop` (real Keycloak, Docker-required) is unaffected and still green.
- **`MASTER_PLAN.md` §3 step 10c** (previously one bundled "the actual UI" bullet) is now split into 10c-1 (this issue, done) through 10c-5 (node-registration screen, CSV import, audit viewer, kill-session/snippet-generator/policy-matrix — none yet spec'd), matching how 10a/10b were already split for issues #13/#15.

1. Read this for orientation.
2. Check out `main`, read `MASTER_PLAN.md` (current plan + decisions log — status source of truth) and `docs/design.md` (strategy/spec rationale) for full context.
3. Check the GitHub issue tracker (`ready-for-agent` label, `SpiderCob/spidercob-gateway`) for what's actually queued and unclaimed — as of this writing, nothing has that label; the next Phase 4 slice needs `/to-spec` first.
4. After finishing an issue — merged, per the workflow in `CLAUDE.md` — update this file with what changed and what's next, commit, and push `context_main` before starting the next issue.
